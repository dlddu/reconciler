# 템플릿: 테스트 시나리오 ↔ E2E 1:1 정합성 (scenario-e2e)

한 레포 안에서 **테스트 문서의 시나리오**와 **E2E 테스트 파일**을 **완전
1:1(전단사)** 로 유지하는 모델. 시나리오 하나당 그 시나리오만 주검증하는 전용 파일
정확히 1개, 모든 파일은 정확히 1개의 시나리오에 대응. 자동화가 곤란한 시나리오는
예외 목록으로 등재해 관리한다. **테스트 문서의 시나리오가 스펙(SSOT)이다.**

**이 모델은 PRD·AC를 읽지 않는다.** 매칭 공간은 시나리오와 E2E 파일 둘뿐이며,
"모든 AC가 시나리오로 커버되는가"(커버리지)도 "시나리오가 참조하는 AC가 실재하는가"
(참조 무결성)도 이 유형의 판정 대상이 아니다. 그 층은 제품 문서 체계
(`product-doc-engineer`·doc-tracker)의 몫이다. 따라서 **PRD만 바뀌면 이 모델은
트리거되지 않는다** — 새 AC가 테스트 문서에 시나리오로 내려오는 순간부터 판정 대상이
된다. 이 경계 덕분에 to-be 범위가 좁아지고, AC 문서의 무관한 갱신이 재검증을 흔들지
않는다.

**범위는 이미 구현된 동작뿐이다.** 시나리오가 기술하는 기능이 아직 구현되지 않아
E2E가 관측할 대상 자체가 없는 시나리오는 이 모델의 drift가 **아니라**
`docs-impl`(미구현)의 관심사다. 그런 시나리오는 "구현 대기"로 등재해 docs-impl로
넘기고, 구현이 착지하면 다음 감지에서 자동으로 1:1 판정 대상으로 돌아온다. **이
루프는 제품 기능을 만들지 않는다** — 산출물은 E2E 테스트, 그것을 돌리는 테스트 인프라,
등재 문서다. 이 경계가 두 유형의 중복 작업을 막는 고정부다. (예외 목록과 구현 대기는
성격이 다르다: 예외는 "E2E로는 검증이 곤란하다"는 **영구 면제**, 구현 대기는 "검증할
것이 아직 없다"는 **임시 보류**. "아직 안 만들었다"는 예외 사유가 아니라 구현 대기
사유이며, 둘을 섞으면 이 경계가 무너진다.)

**테스트 인프라 부족은 이 루프가 닫는다.** 기능은 구현되어 있는데 E2E가 그 상태에
도달할 수단(픽스처·시드·스텁 서버·하네스 헬퍼·E2E용 매니페스트·CI 배선·테스트 진입점)이
없어서 파일을 못 쓰는 시나리오는 미구현도 예외도 아니다 — **공백**이고, 그 인프라를
만드는 것까지 이 모델의 작업 범위다(e2e-mock-policy가 실환경 대체 수단을 직접 만드는 것과
같은 원칙). "검증할 것이 아직 없다"(구현 대기)와 "검증할 수단이 아직 없다"(인프라 선행)를
섞으면 인프라 부채가 구현 대기 표에 숨어 해소 압력이 사라진다.

**개수·범위 숫자는 판정 기준에 넣지 않는다.** 시나리오와 E2E 파일은 계속 추가·삭제되므로,
숫자를 목표나 판정 기준에 박으면 하나가 늘어난 순간 definition이
사실과 어긋난다. 대상이 늘면 to-be 버전이 바뀌어 재평가가 트리거되고,
새 항목도 자동으로 판정 대상에 들어온다.

## 시나리오 식별자의 안정성 (슬롯 채울 때 주의)

시나리오는 문서 안에서 **서수**로만 표기되는 경우가 많다(`### 시나리오 3`). 이 서수는
문서 안에서만 유일하므로 식별자는 반드시 **문서로 한정**해 쓴다(`test-pods.md#시나리오 3`).
그리고 문서 중간에 시나리오를 끼워 넣어 번호가 밀리면 **식별자가 바뀐 것**이므로, 그
task에서 매핑 선언과 등재 표를 함께 갱신해야 한다(개명과 같은 취급). `TC-NNN-NN`처럼
위치와 무관한 안정 ID 체계가 있으면 그쪽을 우선 쓴다. 서수 표기를 쓰는 레포에서는 이
사실을 모델 definition의 "범위 밖 / 비고"에 한 줄로 남긴다.

## 모델 JSON 골격

```json
{
  "id": "tbm_{{SLUG}}-scenario-e2e",
  "metadata": {
    "name": "{{SLUG}} 테스트 시나리오 ↔ E2E 1:1 정합성",
    "description": "{{REPO}}에서 {{TEST_DOCS_PATH}}의 테스트 시나리오({{SCENARIO_ID}})와 {{E2E_UNIT}}를 완전 1:1(시나리오 1개 ↔ 파일 1개)로 유지한다. 자동화가 곤란한 시나리오는 {{EXCEPTION_SSOT}} 예외 목록으로, 미구현이라 검증 대상이 없는 시나리오는 같은 곳의 구현 대기 표로 관리하며, 등재된 시나리오는 drift가 아니다. 미구현의 해소(구현)는 {{SIBLING_DOCS_IMPL}}의 몫이고, AC ↔ 시나리오 층은 이 모델의 판정 대상이 아니다.",
    "tags": ["{{SLUG}}", "test-scenario", "e2e", "consistency"],
    "createdAt": "{{NOW_ISO}}"
  },
  "definition": "<definition 본문 템플릿을 채워 넣기>",
  "toBe": {
    "dataSource": { "type": "github", "repository": "{{REPO}}", "ref": "main" },
    "versionScript": { "runtime": "bash", "code": "<to-be 스크립트>", "timeoutSeconds": 60 }
  },
  "asIs": {
    "dataSource": { "type": "github", "repository": "{{REPO}}", "ref": "main", "subPath": "{{E2E_PATH}}" },
    "versionScript": { "runtime": "bash", "code": "<as-is 스크립트>", "timeoutSeconds": 60 }
  }
}
```

- E2E 도구 태그(예: `maestro`, `playwright`)를 tags에 추가해도 된다.
- 테스트 문서가 한 디렉터리에 모여 있으면 `toBe.dataSource`에 `subPath`를 두고 단일형
  스크립트를 쓴다. 파일명 패턴으로 흩어져 있거나 등재 섹션(`{{TRACKER_DIR}}`)을 함께 묶으면 `subPath`는
  빼고 조합형을 쓴다. 조합형은 슬롯 두 개를 더 쓴다 — `{{TEST_DOCS_DIR}}`(ls-tree로 훑을
  디렉터리)와 `{{TEST_DOCS_RE}}`(그 안에서 테스트 문서만 고르는 정규식).
- **pathspec 글롭(`git ls-tree -r HEAD -- 'docs/x-*.md'`)을 쓰지 않는다.** 매칭에 실패해도
  조용히 빈 목록을 반환하고, 그 sha256(`e3b0c442…`)은 항상 같은 값이라 **어떤 변경도 영영
  감지되지 않는다**. 반드시 디렉터리로 훑은 뒤 `grep -E`로 거른다. 스크립트를 등록하기 전에
  실제 체크아웃에서 한 번 돌려, 나온 값이 `e3b0c442…`가 아니고 매칭 문서 수가 기대와 같은지
  확인한다.

## versionScript

**to-be** (테스트 문서 — 디렉터리면 단일형, 글롭·등재 섹션 조합이면 조합형):

```bash
#!/usr/bin/env bash
# to-be = 테스트 시나리오의 SSOT. {{TEST_DOCS_PATH}} 하위 트리 해시만 사용 → 그 밖(PRD·가치·코드) 변경은 무시된다.
# 런타임이 dataSource.repository({{REPO}})@ref(main)를 체크아웃한 상태를 가정한다.
set -euo pipefail
git rev-parse "HEAD:{{TEST_DOCS_PATH}}"
```

```bash
#!/usr/bin/env bash
# to-be = 시나리오 집합({{TEST_DOCS_PATH}}) + 예외/매핑 등재({{TRACKER_DIR}} 최신 월 파일의 「{{REG_TITLE}}」 섹션).
# 이 둘 밖의 문서(PRD·가치·목업)·코드 변경은 무시된다.
# 파일이 새로 추가돼도 정규식이 자동 포함한다. ls-tree 출력은 경로 정렬이라 결정적이다.
# 런타임이 dataSource.repository({{REPO}})@ref(main)를 체크아웃한 상태를 가정한다.
set -euo pipefail
# <여기에 templates/README.md 「doc-tracker 경로 해석」 조각을 그대로 붙인다>
s="$(git ls-tree -r HEAD -- {{TEST_DOCS_DIR}} | grep -E '{{TEST_DOCS_RE}}' | sha256sum | cut -d' ' -f1)"
t="$(tracker_registry_hash '{{TRACKER_DIR}}' '{{REG_TITLE}}')"
printf 'sc:%s reg:%s\n' "$s" "$t"
```

**as-is** (E2E 트리 해시):

```bash
#!/usr/bin/env bash
# as-is = E2E 테스트 구현. {{E2E_PATH}}/ 하위 트리 해시만 사용 → 그 밖 변경은 무시된다.
# 런타임이 dataSource.repository({{REPO}})@ref(main)를 체크아웃한 상태를 가정한다.
set -euo pipefail
git rev-parse "HEAD:{{E2E_PATH}}"
```

```markdown
# {{SLUG}} 테스트 시나리오 ↔ E2E 1:1 정합성

## 목표
`{{REPO}}` 레포에서 **테스트 문서의 시나리오({{TEST_DOCS_PATH}}의 {{SCENARIO_UNIT}})** 와 **E2E 테스트({{E2E_UNIT}})** 를 **완전 1:1(전단사)** 로 유지한다: 예외 목록·구현 대기 목록에 등재되지 않은 모든 시나리오는 자신을 주검증하는 파일을 정확히 1개 가지며, 모든 매칭 단위 파일은 실재하는 시나리오 정확히 1개를 주검증한다. 따라서 (시나리오 수 − 예외 수 − 구현 대기 수) = (시나리오 매칭 파일 수).

## 무엇이 "맞는 상태"인가 (SSOT)
- **시나리오의 SSOT**는 `{{TEST_DOCS_PATH}}`다 (단위: {{SCENARIO_UNIT}}, 식별: {{SCENARIO_ID}}).
- **E2E 매칭 단위**는 {{E2E_UNIT}}다. {{NON_UNIT}}은 매칭 단위가 아니다.
- **시나리오 ↔ 파일 매핑의 확인 지점**은 {{MAPPING_SSOT}}이며, 매핑은 여기서 기계적으로 확인 가능해야 한다.
- **예외·구현 대기·비-시나리오 매핑 등재의 SSOT**는 {{EXCEPTION_SSOT}}다(예외 목록과 구현 대기 표는 **별도 표**로 둔다 — 영구 면제와 임시 보류를 섞지 않는다).
- **PRD·AC는 이 모델의 SSOT가 아니다.** 시나리오가 어떤 AC를 검증하는지는 테스트 문서가 스스로 적지만, 그 연결의 완전성·정확성은 이 모델이 판정하지 않는다.

## 1:1 매칭 규칙 (판정 기준)
1. **시나리오 → 파일 유일**: 예외 목록·구현 대기 목록(규칙 6) 어디에도 없는 모든 시나리오는 자신을 주검증 대상으로 선언한 파일을 **정확히 1개** 가진다. 0개면 누락, 2개 이상이면 중복 — 둘 다 drift. 테스트 인프라가 없어 파일을 못 쓰는 것도 누락이다(규칙 7).
2. **파일 → 시나리오 유일**: 모든 매칭 단위 파일은 **실재하는 시나리오 정확히 1개**만 주검증 대상으로 선언한다. 여러 시나리오를 묶은 파일은 분리 대상(drift). 테스트 문서에 없는 시나리오를 선언한 파일은 고아와 같이 본다(drift). 셋업 과정에서 다른 시나리오의 화면·경로를 경유하는 것은 검증으로 세지 않는다 — 선언된 검증 대상만 센다.
3. **비-시나리오 파일 허용 유형**: 시나리오 대신 {{NON_SCENARIO_TYPES}}를 검증 대상으로 선언한 파일은 허용하되, {{EXCEPTION_SSOT}}에 등재되어야 한다. 어디에도 매핑되지 않은 파일은 고아(drift). <!-- [선택] 비-시나리오 파일을 허용하지 않으면 "시나리오를 선언하지 않은 파일은 모두 고아(drift)다"로 교체 -->
4. **예외 목록**: E2E로 자동 검증이 곤란한 시나리오(예: {{EXCEPTION_HINTS}})는 {{EXCEPTION_SSOT}}에 **시나리오별 사유와 대체 검증 수단**(수동 QA, 단위/통합 테스트 등)을 적어 등재한다. 등재된 시나리오는 파일이 없어도 drift가 아니다. 등재 없이 파일만 없는 시나리오는 drift. **"아직 구현되지 않았다"는 예외 사유가 아니다** — 그것은 규칙 6의 **구현 대기** 사유다. **"테스트 인프라가 없다"도 예외 사유가 아니다** — 그것은 규칙 7의 인프라 선행이다.
5. **집계 일치**: {{EXCEPTION_SSOT}}의 매칭 집계(시나리오 수·예외 수·**구현 대기 수**·파일 수·공백 목록과 공백별 인프라 선행)가 1~4·6·7의 실제 상태와 일치해야 한다. 사라진 시나리오가 등재 표에 남아 있으면 이 규칙 위반이다. <!-- [선택] 집계 표를 두지 않으면 삭제 -->

## 충돌 시 기본 방향
테스트 문서의 시나리오가 스펙(SSOT)이다.
- 시나리오에 전용 파일이 없으면 → **먼저 그 시나리오의 기능이 이미 구현되어 있는지 확인한다.** 구현되어 있으면 그 상태에 도달할 테스트 인프라가 있는지 확인하고, 없으면 **인프라부터 만든 뒤**(규칙 7) 전용 파일을 신설한다(여러 시나리오를 겸하는 기존 파일은 시나리오별로 분할). 미구현이면 파일을 신설하지 말고 규칙 6의 구현 대기로 등재해 `{{SIBLING_DOCS_IMPL}}`로 넘긴다.
- 한 시나리오에 파일이 여러 개면 → 전용 파일 1개로 병합한다.
- 시나리오 없는 고아 파일이 나타나면 → 의도된 검증이면 테스트 문서에 시나리오를 신설해 문서화하고, 아니면 파일을 제거하거나 허용 유형으로 재매핑한다.
- 파일이 선언한 시나리오가 문서에서 사라졌으면 → 시나리오가 개명·재배치된 것인지 삭제된 것인지 확인해 선언을 갱신하거나 파일을 정리한다.
```
